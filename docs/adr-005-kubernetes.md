# ADR-005 : déploiement sur Kubernetes (k3s, Helm)

- **Statut** : fait pour les PR A (application prête, #12), B (chaîne d'approvisionnement, #15) et C (C1 : images amd64 et arm64, #18 ; C2 : chart Helm, #20 ; C3 : cluster de test, base, proxy de sortie et scénarios, #21), fusionnées les 28 et 29/09/2026. **PR D1** : authentification et entrée réseau (Traefik, oauth2-proxy, jeton vérifié par l'interface), #23, fusionnée le 30/09/2026. **PR D2** : autorisation et traçabilité (rôles, quatre yeux, second facteur, journal d'audit v2, accès d'urgence), cette PR. Chaque PR complète cet ADR.
- **Portée** : le déploiement sur k3s (k3d en local et en CI, plusieurs nœuds) par un chart Helm de niveau production, testé par un vrai cluster à chaque pull request. Aucun déploiement public sur Internet dans cette phase.

## Contexte

Le système tournait sur un poste, en un seul processus : CLI et interface web locale (ADR 004), PostgreSQL par Docker Compose. Le déploiement sur Kubernetes ajoute plusieurs réplicas, des arrêts et des redémarrages de pods, une configuration montée de l'extérieur, et des journaux lus par la plateforme. Toute bonne pratique écartée l'est ici, par écrit ; rien n'est omis en silence.

## Décisions

### Journaux structurés (PR A)

- **JSON sur la sortie standard** dans Kubernetes (`--journaux json`, ou `CDG_JOURNAUX=json` pour tous les conteneurs et les Jobs), texte sur le poste par défaut. Une configuration unique (`adapters/journaux.py`) pour la CLI et pour uvicorn ; aucune dépendance ajoutée (bibliothèque standard).
- **Jamais le texte d'un contrat ni un secret** :
  - une exception n'y laisse que son type et les lignes de code traversées, jamais son message. Starlette relance l'exception après avoir rendu la page d'erreur, et uvicorn la journalisait, message compris ; ce message pouvait citer une donnée reçue ;
  - le journal d'accès : méthode, chemin et code ; ni le corps, ni l'adresse du client ;
  - les bibliothèques ne passent qu'à partir des avertissements.
- **Vérifié** par un vrai serveur uvicorn et un texte témoin dans le contrat : toutes les lignes sont du JSON, le témoin n'apparaît nulle part (`tests/test_journaux.py`).
- **Limite** : les messages d'avertissement des bibliothèques (mistralai, LangGraph, httpx) passent tels quels. Aucun ne cite le contrat dans les tests, mais le code ne peut pas le prouver pour tous leurs chemins.

### Création, revue et expiration sûres entre réplicas (PR A)

- **Un verrou par contrat, dans PostgreSQL** (`ports/locks.py`, `adapters/postgres/locks.py`) : verrou consultatif de session, pris sans attendre (`pg_try_advisory_lock`), clé de 64 bits dérivée de l'identifiant par SHA-256, dans un espace de noms distinct de celui du journal d'audit. Le moteur le prend pour créer un contrat, trancher une revue et expirer un contrat en attente. La seconde demande, où qu'elle vienne, reçoit aussitôt « le contrat … est en cours de traitement » (409 dans l'interface, erreur JSON dans la CLI).
- **Au-delà de la création** : sans le verrou, deux réplicas qui tranchent le même contrat en même temps reprenaient tous deux le graphe. Le journal refusait le second scellement, mais l'état du thread pouvait garder la décision du second, contraire au journal. L'expiration relit chaque contrat sous son verrou et laisse, avec un avertissement, un contrat en cours de revue ailleurs.
- **Si le processus meurt**, sa connexion se ferme et PostgreSQL relâche le verrou (verrou de session, [documentation de PostgreSQL 16](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS)) : un autre réplica peut reprendre l'analyse.
- **Une connexion par verrou**, tenue le temps de l'opération : un verrou consultatif est réentrant pour la session qui le tient ([fonctions de verrou, PostgreSQL 16](https://www.postgresql.org/docs/16/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)) ; deux opérations ne partagent donc jamais une session.
- **Écarté : un regroupeur de connexions en mode transaction** (PgBouncer, ou le `Pooler` de CloudNativePG en mode `transaction`) entre l'application et la base. Il changerait la session sous l'application et ferait tenir le verrou par une autre.
- **Vérifié** par deux vrais processus (`multiprocessing`, méthode spawn), chacun avec son moteur, son checkpointer et ses verrous PostgreSQL : un seul contrat créé et scellé, la seconde demande refusée clairement, puis « existe déjà » ; un processus tué pendant l'analyse relâche le verrou (`tests/test_verrous.py`).

**Connexions à PostgreSQL, par réplica**, avant le pool (état au 28/09, commit du verrou) : chaque opération ouvrait sa connexion et la fermait.

| Opération | Connexions tenues en même temps |
| --- | --- |
| Analyse (une à la fois par réplica, verrou du service) | 1 verrou + 1 checkpointer + jusqu'à 4 recherches (les quatre analystes en parallèle) = 6 ; puis 1 au scellement |
| Revue humaine, expiration | 1 verrou + 1 checkpointer, puis 1 au scellement |
| Lecture (liste, dossier, parcours) | 1 par requête |
| Journal, vérification, rejeu | 1 par requête |

Au plus, par réplica : 6 pour l'analyse en cours, plus une par lecture simultanée. Le nombre de lectures simultanées n'est borné que par le pool de threads de FastAPI (40 par défaut, bibliothèque AnyIO) : jusqu'à environ 46 connexions par réplica. **Décision du 28/09** : un pool de connexions psycopg par processus, de taille réglable, où le verrou compte (section suivante).

### Pool de connexions (PR A, décision du 28/09)

- **Un pool psycopg par processus** pour `app_role` (`adapters/postgres/connexions.py`, psycopg-pool 3.3.3, LGPL-3.0, déclaré en dépendance directe le 28/09 ; il était déjà dans `uv.lock`, tiré par langgraph-checkpoint-postgres). Le checkpointer (`PostgresSaver` accepte un pool), le journal d'audit, la recherche, les verrous de contrat et la sonde de disponibilité y empruntent leurs connexions. Les commandes d'administration (migrations, ingestion) gardent une connexion directe, avec les identifiants administrateur.
- **Réglages** : ceux qu'exige `PostgresSaver` (autocommit, lignes en dictionnaires, pas de requêtes préparées côté serveur) ; les autres usagers ouvrent leurs transactions eux-mêmes et lisent leurs lignes en tuples. Chaque connexion est vérifiée avant d'être prêtée (`check`), pour survivre à un redémarrage ou une bascule de la base. Au retour de chaque connexion, `pg_advisory_unlock_all()` : un verrou de session ne suit jamais une connexion rendue, même si son usager a échoué (vérifié par un test).
- **Pool épuisé** : attente bornée (10 s), puis `ConnectionsExhausted`, rendue en 503 par l'interface, avec `Retry-After: 5`. Jamais une attente sans fin, jamais une erreur 500 sans explication.
- **Taille** : `--connexions` (ou `CDG_CONNEXIONS`), 10 par défaut. Mesure du 28/09 sur la base locale, trois essais, vraie recherche pgvector, vrais poids d'embedding, LLM et extraction en doublures, les quatre domaines à justifier : 29 connexions empruntées par analyse, au plus 4 en même temps. Plafond théorique : 9 (verrou, quatre recherches, quatre écritures du checkpointer en parallèle). Avec 10, une analyse (une seule à la fois par réplica) laisse de la place aux lectures, qui tiennent chacune une connexion quelques millisecondes et attendent leur tour plutôt que d'échouer.
- **Côté PostgreSQL** : `max_connections` ≥ réplicas × taille du pool + tâches (migrations, ingestion) + connexions réservées au superutilisateur. Avec 3 réplicas : 30 + 2 + 3 = 35, sous la valeur par défaut de 100 (réglée dans le chart, PR C).

### Changement de configuration (PR A pour le contrôle, PR C pour le chart)

- **Le risque** : `config/decision.yaml` a une empreinte, posée dans l'état de chaque contrat à son analyse, puis scellée. Après un changement, `resume` refuse un contrat en attente analysé sous l'ancienne empreinte (ADR 004, `docs/exploitation.md`) : déployer une nouvelle configuration rendrait ces contrats impossibles à trancher sans prévenir.
- **Le contrôle** (PR A) : `config-check` liste les contrats en attente d'une revue analysés sous une autre configuration que la courante, et échoue (code 1, erreur JSON avec la liste) s'il y en a. L'administration de l'interface montre la même liste, avec la procédure : trancher sous l'ancienne configuration, ou expirer, ou relancer après le changement. Méthode du service `config_check`, commune aux deux portes (`tests/test_parite.py`).
- **Le déploiement** (PR C) : la configuration vient d'une ConfigMap ; une annotation des pods porte son empreinte, et tout changement de la ConfigMap redéploie les pods (sans elle, les pods garderaient l'ancienne configuration jusqu'à leur prochain redémarrage). Une tâche Helm avant la mise à jour lance `config-check` avec la nouvelle configuration et bloque la mise à jour s'il reste des contrats à trancher ; une valeur du chart permet de passer outre en connaissance de cause (ces contrats seront alors expirés ou relancés).
- **Écarté : migrer l'empreinte des contrats en attente** vers la nouvelle configuration : la décision proposée a été produite par l'ancienne, et le scellement doit dire laquelle.

### Sondes de santé (PR A)

- **Trois sondes, sans logique métier** (`adapters/web/sante.py`), en GET et en HEAD, jamais en cache : `/sante/vie` (le processus répond), `/sante/demarrage` (le modèle d'embedding est chargé ; la sonde de démarrage lui laisse ce temps), `/sante/pret` (démarré, base joignable par le pool, pas en cours d'arrêt). Un échec ne rend que sa raison, jamais son message ; le journal n'en garde que le type.
- **Un port à part** (`web --port-sante`, `--hote-sante 0.0.0.0` dans un pod), servi par un second serveur uvicorn dans un thread à lui : aucune route de l'interface n'y est servie, aucune sonde sur le port de l'interface. Hors du thread principal, uvicorn n'installe pas de gestionnaire de signaux (`Server.capture_signals`, uvicorn 0.54) : seul le serveur de l'interface reçoit l'ordre d'arrêt, les sondes s'arrêtent après lui. Pas de journal d'accès pour les sondes.
- **Pourquoi pas le port de l'interface** : dans la PR D, l'interface n'écoutera que sur 127.0.0.1 dans le pod, derrière oauth2-proxy ; le kubelet appelle l'adresse du pod. Et l'interface contrôle l'en-tête Host, que les sondes n'ont pas à connaître.
- **Écarté : `http.server` de la bibliothèque standard** pour les sondes : sa documentation le déconseille en production.
- **Modèle chargé une fois par processus** : en mode réel, `web` le charge en arrière-plan dès le lancement, et chaque analyse le réutilise. Avant, chaque analyse de l'interface rechargeait les poids depuis le disque.
- **HEAD sur les pages de l'interface** : la RFC 9110 demande à un serveur généraliste d'accepter HEAD là où il accepte GET ; FastAPI ne l'ajoute pas de lui-même, l'interface répondait 405 à `HEAD /`.

### Arrêt propre et reprise des analyses interrompues (PR A)

- **Séquence d'arrêt d'un pod**, de bout en bout :
  1. pause courte avant l'arrêt (`preStop`, dans le chart en PR C), le temps que le pod soit retiré du service ;
  2. à l'ordre d'arrêt (SIGTERM), le drapeau d'arrêt se lève : sonde de disponibilité à 503, toute modification (analyse, décision, expiration) refusée en 503 avec `Retry-After`, à rejouer sur un autre réplica ; la reprise périodique s'arrête ;
  3. uvicorn ferme ses sockets d'écoute et laisse finir les requêtes en cours pendant `web --delai-arret` secondes (60 par défaut), puis annule celles qui restent ;
  4. délai de grâce du pod ≥ pause + délai d'arrêt + marge (chart, PR C).
- **Analyse interrompue** (délai dépassé, processus tué, nœud perdu) : le dernier checkpoint reste, le verrou se libère avec la connexion. Un réplica en mode réel reprend les analyses restées « en cours » au démarrage, puis toutes les `web --reprise-intervalle` secondes (60) : chacune sous son verrou, relue sous le verrou, depuis son dernier checkpoint (`graph.invoke(None, …)`). Un contrat tenu ailleurs est laissé à son réplica.
- **Checkpoints écrits avant l'étape suivante** : chaque appel au graphe passe `durability="sync"`. Par défaut, LangGraph écrit le checkpoint d'une étape pendant l'étape suivante : un processus tué à ce moment laissait un dernier checkpoint incomplet (plus d'étape suivante, pas de résultat), et l'analyse n'était plus reprise. Vu le 28/09 dans un test sur deux vrais processus, une fois sur cinq environ ; plus aucun échec sur vingt essais depuis. Le prix : une écriture en base attendue à chaque étape, négligeable devant un appel au LLM.
- **Rien de perdu, rien de scellé deux fois** : l'étape interrompue est refaite, les autres non ; le scellement est sans doublon (`audit_seal` rejoué, index uniques du journal). Vérifié en un processus (mort simulée au milieu de l'extraction) et avec un vrai processus tué, repris par un autre moteur sur PostgreSQL : un seul enregistrement scellé.
- **Coût** : l'étape interrompue, si elle appelait le LLM, est payée deux fois. La consommation affichée ne compte que l'appel qui a abouti.
- **Reprises comptées, ESCALADE au-delà du maximum** (ajout du 28/09) : une analyse qui fait planter le processus serait reprise à chaque redémarrage, avec un appel au LLM à chaque fois. Chaque reprise est comptée par contrat (port `ResumeCounter`), sous le verrou, **avant** d'être faite : une reprise qui tue le processus est comptée quand même. Au-delà de `interrupted.max_resumes` (3, `config/decision.yaml`), le contrat n'est plus repris : il part en revue humaine, proposé ESCALADE, avec un rapport d'échec (`AnalyseInterrompue`) qui cite l'étape en cours et le nombre de reprises, et un avertissement est journalisé. Il attend alors un humain, et n'est plus jamais repris ; sa décision est scellée comme toute autre.
- **Compteur dans une table, pas dans l'état du graphe** (décision du propriétaire, 28/09) : `contract_resumes` (migration 006), une ligne par contrat, incrémentée en une instruction (`INSERT … ON CONFLICT DO UPDATE … RETURNING`), atomique entre réplicas ; `app_role` sans droit de suppression. L'état du graphe ne s'y prête pas (vérifié, références) : y écrire pendant une analyse en cours rejoue les arêtes d'un nœud et vide les tâches en attente ; `Command(update=...)` répété sur le même checkpoint est ignoré, et sortirait de notre règle « `Command` ne sert qu'à `resume` ». Le nombre de reprises entre dans l'état au moment de l'escalade, avec le rapport d'échec, et il est scellé.
- **L'escalade**, en deux mises à jour de l'état (`bulk_update_state`) : `END` sans valeur vide les tâches en attente en gardant les écritures des tâches finies (les verdicts déjà rendus ne sont ni perdus, ni refaits, ni repayés) ; puis l'escalade est écrite au nom de `decision_gate`, dont l'arête lit `route` : le seul mécanisme de routage du projet, comme après tout échec de nœud escaladé. Vérifié : plantage pendant l'extraction, plantage de deux analystes sur quatre, et de vrais processus tués à chaque reprise sur PostgreSQL.
- **Compte par contrat, sur toute sa vie** : une interruption isolée (un déploiement) coûte une reprise ; le compteur n'est pas remis à zéro quand une reprise aboutit. Un contrat interrompu plus de trois fois, même par des causes différentes, part en revue humaine : l'issue la plus prudente. Si un plantage survient après la décision (explication, scellement), l'escalade ramène le contrat en revue humaine : chaque nouveau tour exige un humain, jamais une boucle automatique.
- **Connexions** : le compteur emprunte une connexion du pool le temps d'une instruction, pendant que le verrou tient la sienne ; il la rend avant la reprise. Le pic mesuré (4) et le plafond théorique (9) ne changent pas.
- **Démonstration** : tout est en mémoire, perdu à l'arrêt ; ni reprise, ni délai de grâce utile.

### Image de l'application (PR A)

- **Deux étapes** (`Dockerfile`) : construction sur l'image de uv 0.12.19 (Debian 13, la version de uv de la CI, `tests/test_image.py` le vérifie), exécution sur distroless `cc-debian13:nonroot`. Les deux bases sont figées par l'empreinte de leur index multi-architecture (amd64, arm64) ; aucune directive `# syntax`, qui tirerait un frontal de construction non figé.
- **Python** : CPython 3.12.14, géré par uv (python-build-standalone, empreinte vérifiée par uv), copié dans l'image finale. Retirés, car ils ne servent qu'à installer ou à développer : pip, ensurepip, IDLE, Tk, 2to3, la suite de tests de CPython, les en-têtes C, les scripts `pip`, `pydoc`, `python3-config`.
- **Installation stricte** : `uv sync --locked --no-dev --no-build --no-install-project`. Tout vient de uv.lock, avec ses empreintes ; aucun paquet n'est construit depuis ses sources. Le projet lui-même n'est pas installé : construire son paquet tirerait `hatchling`, que uv.lock ne fige pas. Son code est lu depuis `/app/src` (`PYTHONPATH`), compilé en bytecode validé par empreinte du source.
- **Disposition du dépôt conservée** (`/app/src`, `/app/config`, `/app/data`, `/app/migrations`) : le code trouve sa configuration, le jeu de démonstration, le corpus et les migrations par rapport à son propre chemin. Le contexte de construction (`.dockerignore`) n'admet que ces dossiers, `pyproject.toml`, `uv.lock` et la licence : jamais `.env`, `.git`, les poids du modèle ni les caches.
- **Utilisateur non root, numérique** : `USER 65532:65532`, l'utilisateur `nonroot` de distroless ; Kubernetes peut ainsi vérifier `runAsNonRoot` sans lire `/etc/passwd`. Le code et Python appartiennent à root : le processus les lit, sans pouvoir les modifier, même hors lecture seule (vérifié).
- **Système de fichiers racine en lecture seule** : rien n'est écrit hors de `/tmp` (volume éphémère dans le chart, PR C) ; `PYTHONDONTWRITEBYTECODE=1`. Vérifié : lancée avec `--read-only --tmpfs /tmp --cap-drop ALL --security-opt no-new-privileges`, l'image charge ses dépendances natives (onnxruntime, libpq de psycopg, numpy, tokenizers), sert ses sondes, et s'arrête proprement à `docker stop` (code 0).
- **Aucun outil inutile** : ni shell, ni `apt-get`, ni `dpkg`, ni uv, ni pip (vérifié : chacun introuvable). Les sondes du chart seront des `httpGet`, la pause avant l'arrêt une action `sleep` de Kubernetes : rien n'exige de shell. Pour diagnostiquer un pod : un conteneur éphémère (`kubectl debug`).
- **Processus 1** : Python, lancé en forme exec (`ENTRYPOINT ["python", "-m", "cdg.cli"]`, `CMD ["web"]`) ; uvicorn installe ses gestionnaires de SIGTERM et SIGINT. L'application ne lance aucun sous-processus : pas de processus d'init pour récolter des zombies.
- **Environnement par défaut** : journaux JSON (`CDG_JOURNAUX=json`) ; `HF_HUB_OFFLINE=1`, aucun téléchargement du modèle au démarrage ; `ORT_DISABLE_TELEMETRY=1`, que l'adaptateur pose aussi ; `LANGSMITH_TRACING=false` ; `CDG_COMMIT`, le commit de la construction, scellé avec chaque décision (PR D2). Aucun secret, aucune clé, vérifié sur l'image construite.
- **Journaux JSON de bout en bout** : en `--journaux json`, l'adresse de l'interface et l'avertissement d'écoute non locale passent par le journal, et le résultat final d'une commande tient sur une ligne. Au terminal (journaux texte), rien ne change.
- **Interface sur 127.0.0.1 dans le conteneur** : même publiée, elle ne répond pas depuis l'extérieur (vérifié) ; elle sera jointe par oauth2-proxy, dans le même pod (PR D). Seules les sondes écoutent sur l'adresse du pod.
- **Taille** : 423 Mo (arm64), surtout onnxruntime, numpy et leurs bibliothèques. Les poids du modèle d'embedding (2,2 Go) n'y sont pas : image dédiée en PR B.
- **Vérification** : `tests/test_image.py`. Les tests du Dockerfile tournent avec la suite ; ceux de l'image construite (marqueur `image`, `--image ÉTIQUETTE`) dans le job `image` de la CI, sur amd64, et dans `scripts/check.sh`, sur l'architecture du poste. Publication sur ghcr.io, scan, inventaire, signature et provenance : PR B. Mise à jour des bases : à la main dans cette PR ; Dependabot en PR B (ci-dessous).
- **Écarté : `python:3.12-slim`** (image officielle Docker) et `debian:trixie-slim` (celle de l'exemple de uv) pour l'exécution : shell, `apt`, `dpkg` et pip y restent, soit autant d'outils inutiles et de paquets à surveiller. Elles restent la base la plus simple, et la plus courante ; distroless est publiée et signée par son projet (GoogleContainerTools), pas par Docker.
- **Écarté : `distroless/python3-debian13`**, dont le Python (3.13, celui de Debian) n'est pas celui du projet.
- **Écarté : un processus d'init** (tini, `dumb-init`) : rien à récolter, et un outil de plus.

### Chaîne d'approvisionnement (PR B)

Décisions du 28/09 (propriétaire), réalisées dans la PR B.

- **Images de base par Dependabot** : écosystème `docker` sur le dossier racine, le lundi à 6 h comme les autres ; il propose les nouvelles empreintes (et versions) des bases du `Dockerfile`, et chaque proposition passe par la CI avant fusion (tests, construction, signatures des bases, inventaire, scan). Hors de Dependabot, délibérément : l'image PostgreSQL, qui touche aux données (`docker-compose.yml` n'est pas lu par l'écosystème `docker`, et `docker-compose` n'est pas configuré), et uv, mis à jour avec celui de la CI et du poste (`ignore`) ; l'étape de construction, sur l'image de uv, ne part pas dans l'image finale. `tests/test_chaine_approvisionnement.py` le vérifie, ainsi que l'épinglage de toutes les actions des workflows.
- **Signatures des images de base vérifiées avant la construction** (`scripts/chaine.py bases`, job `image` et `scripts/check.sh`) : distroless par `cosign verify`, avec l'identité et l'émetteur publiés par le projet (`keyless@distroless.iam.gserviceaccount.com`, `https://accounts.google.com`) ; uv par `gh attestation verify`, attestation de provenance du workflow d'astral-sh/uv, comme le recommande sa documentation. Une signature absente ou différente arrête la construction, avec l'image en cause ; une base sans politique de vérification est refusée, jamais ignorée. cosign tourne dans son image officielle, figée par version et empreinte : le même binaire en CI et sur le poste, rien à installer. Deux échecs, distingués depuis le 29/09 et qui font tous deux échouer la vérification : **signature invalide** (erreur de sécurité, avec l'identité attendue), ou **vérification impossible** (cause d'environnement reconnue dans le message de l'outil : réseau, service indisponible, `gh` non authentifié, Docker indisponible). Une cause non reconnue reste une signature invalide.
- **Inventaire et scan de l'image** (`scripts/chaine.py inventaire` et `scan`, job `image` et `scripts/check.sh`, après les tests de l'image) : Syft produit l'inventaire en SPDX (attesté à la publication) et au format de Syft, que Grype lit plus complètement (distribution, empreintes). Grype scanne l'inventaire lui-même : la liste publiée est celle qui a été scannée. Échec sur une faille critique ou haute qui a un correctif (`--only-fixed --fail-on high`) ; les failles sans correctif (glibc, zlib de Debian 13 au 28/09) ne bloquent pas, car rien ne permettrait de les corriger. La base de failles de Grype est gardée dans un volume Docker (`cdg-grype-db`) entre deux scans du poste.
- **Exceptions justifiées, datées, expirantes** (`securite/exceptions-vulnerabilites.yaml`) : une faille, un paquet, une version exacte, un motif, une date de décision et une date d'expiration, 90 jours au plus après. Une exception incomplète ou expirée fait échouer le scan, avec la faille et la date. La seule exception au 28/09 : CVE-2026-82049 sur CPython 3.12.14 (références), jusqu'au 28/10/2026.
- **Aussi chaque lundi** : le job `image` rejoint `audit` dans le déclenchement planifié. Une faille publiée entre deux commits, ou une exception expirée, est vue sans attendre le suivant.
- **Outils en conteneurs figés** : Syft, Grype et cosign tournent dans leurs images officielles, figées par version et empreinte (`scripts/chaine.py`), au-delà de tous leurs avis publiés (`tests/test_chaine_approvisionnement.py`). Le même binaire en CI et sur le poste, rien à installer ; leurs mises à jour sont manuelles, comme celle de l'image PostgreSQL. Écarté : les actions `anchore/sbom-action` et `anchore/scan-action`, qui ne tourneraient qu'en CI.
- **Publication** (job `publication`, après une fusion dans `main` seulement, une fois tous les autres jobs verts) : l'image publiée est celle que le job `image` a construite, testée, inventoriée et scannée, passée d'un job à l'autre (`docker save`, artefact d'un jour), jamais reconstruite. Poussée sur `ghcr.io/sifir-gun/contract-decision-graph`, étiquetée `sha-<commit>`, jamais `latest` ; son empreinte est relue dans le registre, et c'est elle que le chart référencera (PR C).
- **Signature et attestations** : `cosign sign` sans clé, par l'identité OIDC du workflow (`…/.github/workflows/ci.yml@refs/heads/main`, émetteur `https://token.actions.githubusercontent.com`) ; attestation de provenance SLSA et attestation de l'inventaire SPDX (celui qui a été scanné) par `actions/attest`, poussées dans le registre à côté de l'image. Le job vérifie ensuite ce qu'il a publié (`cosign verify`, deux `gh attestation verify`), et inscrit l'empreinte dans le résumé du run.
- **Droits** : le workflow reste en `contents: read` ; seul le job de publication reçoit `packages`, `id-token` et `attestations` en écriture. Aucune expression `${{ }}` dans ses scripts : les valeurs passent par l'environnement (injection de script). Pas de trace de stockage : réservée aux dépôts d'organisation.
- **Étiquettes OCI** de l'image (`source`, `licenses`, `title`, `description`) : la source relie le paquet au dépôt. La révision n'y est pas, pour garder la même construction en CI et sur le poste : elle est dans l'attestation de provenance.
- **Deux architectures, amd64 et arm64** (décision du 28/09, PR C1) : le job `image` tourne en matrice, chaque architecture sur son runner natif (`ubuntu-24.04`, `ubuntu-24.04-arm`), sans émulation ni plateforme forcée, et chacune passe la même chaîne (signatures des bases, construction, tests de l'image, notices, inventaire, scan). La publication pousse les deux images testées, les réunit dans un index (`docker buildx imagetools create`), vérifie qu'il ne désigne que `linux/amd64` et `linux/arm64`, signe l'index et chaque image (`cosign sign --recursive`), atteste la provenance de l'index et l'inventaire de chaque architecture, puis vérifie les trois empreintes. Le chart référence l'empreinte de l'index. Mécanique répétée sur un registre local jetable avant la fusion.
- **Visibilité du paquet** : public dès la première publication, contrairement à ce qu'annonce la documentation de GitHub (références, observation du 28/09) ; irréversible. L'image de l'application a donc été inspectée couche par couche après coup (aucun secret, aucun fichier `.env`, aucune clé du projet, rien du poste ni de l'identité du propriétaire ; faux jetons de test de mistralai et chemins de construction des roues tierces seulement), et celle du modèle avant sa publication. Le chart (PR C) tire les images sans secret.
- **Limite connue** : le job de publication ne peut pas tourner avant la fusion (il exige l'identité de `main` et le droit d'écrire dans le registre). Tout ce qui peut l'être est vérifié avant : ses droits, l'ordre de ses étapes, les versions, l'aller-retour de l'image par `docker save` et `docker load` (même identifiant), la lecture de l'empreinte ; sa première exécution se lit après la fusion.
- **Image du modèle d'embedding** (`docker/modele/Dockerfile`, `ghcr.io/sifir-gun/contract-decision-graph/modele-embedding`) : `FROM scratch`, le cache de Hugging Face tel que le remplit `cdg.cli fetch-embedding-model` (instantané, `refs/main`, copie à plat que charge l'adaptateur) et la notice de licence (`LICENCE-MODELE.md` : sources, licences MIT, texte de celle de microsoft/unilm). Ni système, ni outil, ni inventaire ni scan : il n'y a pas de logiciel dedans. Montée en lecture seule à `EMBEDDING_CACHE_DIR` (volume `image`, PR C).
- **Figée par le contenu, pas par la révision** : `docker/modele/empreintes.sha256` fige les empreintes SHA-256 des six fichiers chargés ; `scripts/modele.py verifier` refuse un fichier modifié, absent ou en trop, avec son nom, avant toute construction. La révision du dépôt amont a changé le 24/09/2026 sans toucher aux poids (références) : la figer aurait bloqué pour rien, sans protéger mieux. Un changement de poids fait échouer la vérification ; il exige de réindexer le corpus, et se décide.
- **Liens physiques conservés** : l'adaptateur charge les poids par une copie à plat en liens physiques, qu'il refait s'ils manquent ; sur un volume en lecture seule, il échouerait. BuildKit les garde dans la couche de l'image (2,25 Go, pas 4,5), et un test le vérifie sur le contenu extrait.
- **Test de bout en bout** (`tests/test_modele.py`, marqueur `modele`) : le contenu de l'image, extrait tel quel (`docker export`), est conforme au manifeste, garde ses liens physiques, tout y est lisible par l'utilisateur de l'application (fichiers de root, lus par 65532 dans le pod), et l'application le charge monté en lecture seule, système de fichiers racine en lecture seule, **sans réseau** (`--network none`) : vecteur de 1024 dimensions. Le montage d'image de Docker 29 est encore expérimental (références) : le contenu est extrait par root dans un volume Docker, là où tournent les conteneurs, avec les droits de l'image ; un dossier de l'hôte ne vaut pas (dossiers de pytest en 0700, droits ignorés par Docker Desktop : correction du 28/09, run 36397656485).
- **Artefacts du téléchargement exclus** (`docker/modele/Dockerfile.dockerignore`, lu par BuildKit pour ce seul Dockerfile) : les verrous (`.locks/`) et la liste des fichiers du dépôt (`trees/`, écrite en 0600 par huggingface_hub, illisible par l'application) ne servent qu'au téléchargement.
- **Workflow à part** (`.github/workflows/modele.yml`), seule exception à « aucun téléchargement du modèle en CI » : sur une pull request qui touche l'image du modèle, son script ou le chargement des poids, il télécharge (2,2 Go), vérifie, construit et teste, sans aucun droit d'écriture ; à la demande depuis `main`, il fait de même, puis publie (étiquette `sha-<commit>`), signe sans clé, atteste la provenance et vérifie ce qu'il a publié. Des outils préinstallés inutiles sont retirés du runner d'abord, pour l'espace disque (poids, image, extraction).
- **Déclenchement** : la publication est un geste du propriétaire (`gh workflow run modele.yml --ref main`, ou le bouton « Run workflow »), après la fusion ; l'empreinte publiée est dans le résumé du run, et le chart la référencera (PR C).
- **Notices de licence** (décision du 28/09 ; `licences/`, `tests/test_licences.py`) : chaque composant redistribué dans une image publique porte sa licence. L'inspection de l'image publiée a trouvé deux manques : quatre paquets Python dont la roue ne contient aucun texte (flatbuffers et tokenizers, Apache-2.0 ; langsmith et loguru, MIT), et les bibliothèques que python-build-standalone lie dans Python (OpenSSL, SQLite, libffi…), dont l'archive installée ne porte que la licence de CPython. Leurs textes, copiés tels quels depuis leur source (tag et commit de chaque projet ; archives complètes de la publication 20260924 de python-build-standalone), sont dans `licences/`, copié dans l'image sous `/app/licences/`, avec leur provenance (`licences/PROVENANCE.md`).
- **Test des notices** : avec la suite, la provenance (publication de python-build-standalone égale à celle que uv installe pour la version figée ; version de chaque paquet égale à celle de `uv.lock`, pour qu'une mise à jour fasse relire sa licence) ; sur l'image de l'application construite (marqueur `image`), chaque paquet Python porte sa licence (dans sa roue, dans le dossier du paquet, ou dans `licences/`), chaque paquet Debian son `copyright`, Python et ses bibliothèques liées les leurs, avec AGPL, HTMX et corpus ; sur l'image du modèle (marqueur `modele`), la notice MIT du modèle et de sa conversion ONNX. Contre-épreuve : lancé sur l'image publiée avant la correction, le test nomme les quatre paquets et les licences de Python manquantes.
- **langsmith** : client de traçage de LangSmith, tiré par langchain-core, présent dans l'image. Il ne trace que si `LANGSMITH_TRACING` (ou `LANGCHAIN_TRACING_V2`) vaut `true` ; l'image pose `LANGSMITH_TRACING=false`, `.env.example` aussi, et aucune clé n'est fournie. Vérifié (`tests/test_embeddings.py`) : une analyse complète ne tente aucune connexion, sans variable comme avec la configuration de l'image, sous une garde portable qui compte toute résolution de nom ou connexion de Python (en CI) et sous le bac à sable du noyau de macOS (sur le poste) ; leurs témoins, traçage activé avec une clé fictive, voient la tentative. Dans le cluster, le proxy de sortie (PR C) ne laissera passer que l'API de Mistral : `api.smith.langchain.com` y serait refusé de toute façon.
- **Image du modèle en deux architectures** : elle ne contient que des données, sa variante arm64 se construit donc sans émulation (`FROM scratch`, aucune commande exécutée) sur le runner amd64, et ses couches doivent être exactement celles de la variante testée (`RootFS.Layers` comparés ; vérifié sur le poste, dans l'autre sens). Même index, même signature récursive, mêmes vérifications que l'application.

### Chart Helm (PR C2)

Le chart (`chart/contract-decision-graph/`) et sa validation statique, sans cluster : k3d, CloudNativePG, le proxy de sortie (Smokescreen) et les scénarios sont venus en PR C3 (plus bas). Mode d'emploi et valeurs : `chart/contract-decision-graph/README.md`.

- **Outils figés** : helm 4.3.0 (au-delà des avis publiés, jusqu'à 4.1.3), installé sur le poste par Homebrew (`brew install helm`, même version) et en CI depuis l'archive officielle, vérifiée par son empreinte ; kubeconform 0.8.0 et kube-linter 0.8.3 dans leurs images officielles, figées par version et empreinte. Kubernetes visé : 1.36.4, canal stable de k3s.
- **Validation** (`scripts/chart.py verifier`, job `chart` de la CI, `scripts/check.sh`) : `helm lint --strict` et rendu de trois variantes (réel, démonstration, repli par copie du modèle) ; kubeconform, strict, contre les schémas de Kubernetes 1.36.4 ; kube-linter, toutes vérifications actives, sur chaque variante à part. Réunies, les variantes se mêlent : kube-linter rapprochait le budget d'interruption du rendu réel du Deployment de la démonstration. `tests/test_chart.py` vérifie ensuite les garanties du rendu ; il le lit avec un chargeur YAML qui refuse une clé en double, car PyYAML garde la dernière sans rien dire (les étiquettes des pods étaient en double, kubeconform les refusait).
- **Pods** : Pod Security « restricted » (utilisateur 65532, seccomp `RuntimeDefault`, racine en lecture seule, aucune capacité, pas d'élévation) ; compte de service dédié, sans jeton monté ; `/tmp` en volume éphémère borné ; images par empreinte seulement ; poids du modèle en volume `image`, en lecture seule, ou copiés par des conteneurs d'initialisation (`modele.montage=copie`).
- **Secrets en fichiers, jamais en variables d'environnement** (décision du 28/09 ; CIS 5.4.1, kube-linter `read-secret-from-env-var`, qui passe) :
  - créés hors du chart, qui ne fait que les nommer ; aucune valeur secrète dans les valeurs (testé) ;
  - montés par un volume projeté, en lecture seule, dans `/run/secrets/cdg`, un fichier par secret nommé comme sa variable (`APP_DB_PASSWORD`, `MISTRAL_API_KEY`, `POSTGRES_USER`, `POSTGRES_PASSWORD`). Chaque conteneur ne reçoit que les siens : la clé de Mistral pour l'interface, les identifiants administrateur pour les migrations et l'ingestion ;
  - mode `0440` et `fsGroup: 65532` : le kubelet de Kubernetes 1.36 crée pour root les fichiers d'une source Secret d'un volume projeté ; seul un jeton de compte de service prend l'utilisateur du pod (`pkg/volume/projected/projected.go`). L'utilisateur 65532 les lit donc par son groupe ; les autres, rien ;
  - côté application (`settings.secret`, bibliothèque standard seulement) : le fichier s'il existe, espaces et fins de ligne retirés, sinon la variable d'environnement (CLI, poste, `.env`). Un fichier présent mais vide, illisible ou mal encodé est une erreur, jamais un repli sur la variable ; aucun message ne reprend la valeur, et l'exception d'origine n'est pas chaînée (testé jusqu'à la sortie de la CLI).
- **Dimensionnement**, d'après la mesure du 28/09 (`scripts/mesure_memoire.py`, journal) :
  - réplica réel : environ 1 550 Mio de mémoire anonyme une fois prêt, 16 Mio de plus par analyse. Requête de 2 Gi, limite de 3 Gi, pour garder de la marge au cache de fichiers et aux pics ; limite portée à 4 Gi en PR C3 (pic de chargement du modèle, plus bas) ;
  - CPU : requête de 1, limite entière de 2. Le nombre de fils de l'embedder suit la limite (`CDG_FILS_EMBEDDING`) : sous 2 CPU, une requête prend 3,6 s avec 2 fils, contre 9,7 s avec les fils par défaut d'onnxruntime ;
  - ingestion : 2 290 Mio au pic. Requête de 3 Gi, limite de 3,5 Gi, 2 CPU ; limite portée à 4 Gi en PR C3, avec des lots de 16 (plus bas) ;
  - démonstration : 73 à 107 Mio. Requête de 128 Mi, limite de 256 Mi ;
  - autres tâches : requête de 256 Mi, limite de 512 Mi ; copie des poids : 32 Mi, limite de 64 Mi.
- **Disponibilité** : deux réplicas, sans autoscaling (la charge est de l'attente du LLM, bornée par le quota de Mistral) ; mise à jour progressive sans interruption (un pod de plus, jamais un de moins) ; budget d'interruption d'un pod disponible, qui laisse évincer un pod pas prêt ; répartition sur des nœuds différents, stricte par les contraintes de topologie (écart d'au plus un pod), avec une anti-affinité préférée seulement : exigée, elle bloquerait la mise à jour progressive quand le cluster a autant de nœuds que de réplicas, le pod en plus n'ayant aucun nœud libre ; trois sondes sur le port des sondes ; pause avant l'arrêt, puis délai de grâce égal à la pause, plus le délai d'arrêt, plus une marge.
- **Configuration** : une ConfigMap, dont l'empreinte, portée par les pods, les relance à chaque changement ; la tâche de contrôle refuse une mise à jour qui laisserait des contrats en attente impossibles à trancher (`passerOutre`, en connaissance de cause).
- **Réseau** : tout refusé par défaut. En sortie, l'interface ne joint que le DNS, PostgreSQL et le proxy ; les tâches, le DNS et PostgreSQL ; le test Helm, le DNS et les sondes. Aucune entrée hors du test. Les règles des tâches et leur compte de service n'existent qu'avec des tâches : une règle qui ne désigne aucun pod est orpheline, comme en démonstration.
- **Tâches Helm** : migrations avant l'installation et chaque mise à jour, ingestion après, contrôle de configuration avant une mise à jour ; tentatives bornées, délai maximal, nettoyage automatique. Une tâche en échec reste, pour le diagnostic, jusqu'à son délai de conservation.

#### Exceptions aux bonnes pratiques (kube-linter)

Toutes les vérifications intégrées sont actives (`addAllBuiltIn`). Une exception qui tient à un objet est posée sur lui, par l'annotation `ignore-check.kube-linter.io/<vérification>` (syntaxe de `docs/configuring-kubelinter.md`, 0.8.3), avec sa justification pour valeur ; `tests/test_chart.py` fixe la liste par objet et exige une justification. Seules celles qui ne visent aucun objet sont dans `chart/.kube-linter.yaml` (décision du 28/09).

- **Sur les Jobs et le Pod du test Helm** :
  - `restart-policy` : `Never`, pour que chaque tentative ait son pod et que le journal d'une tentative ratée reste lisible ; le test Helm n'est jamais retenté ;
  - `no-liveness-probe` et `no-readiness-probe` : des tâches qui s'exécutent jusqu'au bout, bornées par leur délai, sans service ni trafic à recevoir.
- **Sur le Deployment, les Jobs et le Pod de test** :
  - `dnsconfig-options` (`ndots: "2"` recommandé) : ces pods ne résolvent que des noms internes au cluster ; `api.mistral.ai` est résolu par le proxy de sortie, dont le pod reçoit cette configuration DNS (PR C3, chart `cdg-proxy`) ;
  - `no-node-affinity` : aucune contrainte de matériel ni de zone ; n'importe quel nœud convient, amd64 comme arm64.
- **Sur le Deployment** : `minimum-three-replicas`. Deux réplicas par défaut : un réplica réel occupe environ 1 550 Mio mesurés (requête de 2 Gi) ; un troisième réserverait 2 Gi de plus pour une charge bornée par le quota de Mistral, et le budget d'interruption garde un pod disponible.
- **Sur les règles réseau `web` et `taches`** : `dangling-networkpolicypeer-podselector`. Le proxy de sortie et PostgreSQL sont rendus par leurs propres charts (`cdg-proxy`, `cdg-postgres`, PR C3) ; leurs pods existent hors du rendu.
- **Dans la configuration** : `schema-validation` (kubeconform la fait déjà, figé et strict, contre la version visée ; celle de kube-linter télécharge les schémas de la branche principale, sans version, et échoue en TLS depuis son image) ; conventions d'une organisation (`required-annotation-email`, `required-label-owner`) ; ordre des clés (`sorted-keys`).
- **Satisfaites plutôt qu'exclues** : `read-secret-from-env-var` (secrets en fichiers), `no-anti-affinity` (anti-affinité préférée), `restart-policy` du Deployment (`Always` écrit). `priority-class-name` ne vise aucun objet : elle ne signale qu'une classe de priorité invalide, et le chart n'en pose pas. `env-value-from` n'a plus d'objet : plus aucune variable ne lit un Secret.

#### Base (CloudNativePG)

- **Chart `cdg-postgres`** : `Cluster` PostgreSQL 16.15 avec pgvector (image `standard` de CloudNativePG, par étiquette et empreinte : l'admission de l'opérateur refuse une image désignée par sa seule empreinte), WAL archivés en continu et sauvegarde nocturne par le greffon (`ObjectStore`, `ScheduledBackup`), règles réseau ; restauration par `restauration.source`.

Ce sont les garanties exigées de `setup-db`, sans code à nous ; la gestion déclarative convient donc, et c'est elle que le cluster utilise. La migration 001 ne crée le rôle que s'il manque : Docker Compose continue de fonctionner.
- **Rotation du mot de passe sans redémarrage** (décision du 29/09) : le pool figeait sa chaîne de connexion au démarrage, et une nouvelle connexion aurait gardé l'ancien mot de passe (constat de relecture, avant la fusion). Entre l'application du nouveau mot de passe en base et la mise à jour du fichier par le kubelet, une nouvelle connexion échoue ; les connexions ouvertes continuent de servir (`docs/exploitation.md`).
- **`setup-db` amorce une base vide** : si la 001 n'y est pas passée, toutes les migrations dans l'ordre (001 à 006) ; sinon les idempotentes, sans effet ; relancé, rien ne change (testé sur une base neuve). Si le rôle manque encore (ni opérateur, ni Compose), `setup-db` le crée avec un vérificateur SCRAM-SHA-256 calculé côté client (bibliothèque standard ; 4096 itérations, sel de 16 octets ; identique à celui de libpq à sel égal, testé), dans une transaction qui suspend `log_statement` et `log_min_error_statement` : le mot de passe n'atteint jamais le serveur (testé sur les requêtes envoyées, la trace du protocole sous Linux et les journaux de l'application).
- **Restauration** : un nouveau cluster amorcé depuis les sauvegardes de l'ancien ; l'application y est basculée par une mise à jour (`base.hote`, `base.selecteur`, `base.administrateur.secret`), puis `verify --expect-head` compare la chaîne à la tête relevée avant la sauvegarde. Procédure : `docs/exploitation.md`.

#### Défauts trouvés par le cluster, corrigés

- **Mémoire** (mesure du 28/09, dans le cluster) : le chargement du modèle monte à 2,55 à 2,65 Gio avant de redescendre à 1,55 Gio ; l'interface, limitée à 3 Gi, était tuée (OOMKilled). fastembed embarque par lots de 256 par défaut : l'ingestion dépassait 3,5 Gi. Avec des lots de 16 (`embedding.lot`, `--lot-embedding`, `CDG_LOT_EMBEDDING`), 2,9 Gio au pic ; avec 64, plus de 3,7. Limites : 4 Gi pour l'interface comme pour l'ingestion.
- **Durée de l'ingestion** : 64 extraits, 18 min 24 s dans k3d sur 2 CPU (environ 80 s par lot de 16 sur le poste). L'installation attend toute la tâche (3 600 s, son délai) ; le job `cluster` a 90 minutes. Les mises à jour des scénarios ne réindexent pas un corpus inchangé (`taches.ingestion.active=false`) ; même réglage en production pour une mise à jour qui ne touche pas au corpus. Piste : n'embarquer que les extraits absents de la base.
- **Règle réseau des tâches** : ressource ordinaire, elle n'était mise à jour qu'après les crochets `pre-upgrade`. Une mise à jour qui change de base (restauration) laissait la tâche de migrations sous l'ancienne règle, qui ne menait qu'à l'ancienne base. Elle devient un crochet, comme le compte des tâches, posé avant elles. Comme lui, `helm uninstall` ne la supprime pas (ressource de crochet) : sans effet, elle ne vise que les pods des tâches.
- **Installation rejouable** : relancée, elle tirait de nouvelles clés S3 ; SeaweedFS, qui ne relit ses identités qu'au démarrage, refusait alors l'archivage des WAL. Les secrets déjà créés sont repris ; une clé attendue qui manque est une erreur.
- **Disque des nœuds** : c'est celui de Docker, partagé (poste, runner), et un nœud y stocke le modèle deux fois (couches et contenu décompressé, 2,25 Go chacun). k3s 1.36.4 évince à 5 % libres puis récupère 10 % de plus (`pkg/daemons/agent/agent.go`) : sur le disque de 110 Go du poste, rempli à 86 % par d'autres projets, tout le cluster a été évincé pendant `check.sh`. Seuils absolus sur chaque nœud (éviction sous 1 Gi libre, 500 Mi récupérés), les autres signaux restant à zéro comme chez k3s ; syntaxe des filtres de nœuds lue dans le code de k3d (`cmd/util/filter.go`), que son aide contredit.
- **Disque du runner** : 14 Go garantis sur un runner public (documentation de GitHub), 85 Go libres constatés le 29/09 ; consommés par le cluster en CI, le même jour : 21 Go (85 Go libres avant le cluster, 64 après les douze scénarios). Besoin du cluster au pire, calculé sur la taille mesurée des images (`scripts/cluster.py`, `disk_need_gb`) : 28,4 Go pour trois nœuds, chaque image sur chaque nœud en couches compressées (modèle : 1,33 Go) et en contenu décompressé (2,25 Go), nos images en plus dans le registre local et sur l'hôte, les données et le seuil d'éviction. Le job ne retire des outils préinstallés (Android, .NET, GHCup, bundle CodeQL) que sous 30 Go libres, et relève l'espace restant en fin de job ; jamais dans `check.sh`.
- **Crochets et désinstallation** : Helm ne supprime à la désinstallation que les ressources ordinaires ; le compte et la règle réseau des tâches et la configuration à venir survivaient à `helm uninstall`. Chaque ressource de crochet est supprimée après son crochet ; les journaux des tâches sont d'abord recopiés sur la sortie de Helm. Une tâche en échec reste, pour le diagnostic, jusqu'à son délai de conservation ; son nettoyage après désinstallation est documenté et testé (scénario 8).
- **`check.sh --sans-cluster`** : le profil local monte à 7 Go sur les 8 de la VM Docker du poste, qui a redémarré le 29/09 pendant une installation. L'option saute le cluster en l'annonçant ; seul le job `cluster` de la CI le vérifie alors.

#### Scénarios (`tests/test_cluster.py`, marqueur `cluster`)

Sur le même cluster, dans l'ordre du fichier ; les analyses passent par l'interface, par redirection de port, comme pour un utilisateur.

1. **Deux réplicas sur deux nœuds** ; **création concurrente** d'un même contrat par les deux : une réussite, un refus (409), un seul thread, un seul scellement.
2. **Arrêt propre pendant une analyse** : la requête en cours finit ; **pod tué pendant une analyse** : reprise par l'autre réplica depuis son dernier checkpoint, scellée une seule fois.
3. **Mise à jour sans interruption** : une sonde interroge le service pendant toute la mise à jour, aucune requête perdue.
4. **Retour arrière** vers la révision précédente, rien de perdu.
5. **Blocage réseau** : sortie directe refusée par les règles réseau ; domaine hors liste refusé par le proxy (407) ; **adresse d'API autre que Mistral** (le serveur factice, sous les valeurs de production du proxy) : rapport d'échec explicite, ESCALADE et revue humaine, aucune requête reçue.
6. **Rotation du mot de passe d'`app_role`** : les mots de passe témoins (celui de l'installation, puis celui de la rotation), en clair et en base64, n'apparaissent dans aucun journal (tous les conteneurs du cluster : opérateur, instances PostgreSQL, application ; tâches recopiées par Helm), avant et après la rotation. L'ancien mot de passe est refusé ; les connexions d'`app_role` sont coupées côté serveur, et chaque réplica en rouvre avec le nouveau pour analyser et sceller un contrat, sans redémarrage ; la tâche de contrôle se connecte avec lui.
7. **Contrôle de configuration avant une mise à jour** : refusée tant qu'un contrat attend sous l'ancienne configuration, rien déployé ; acceptée avec `passerOutre`.
8. **Authentification et entrée** (PR D1) : douze scénarios, section suivante.
9. **Sauvegarde puis restauration** : archivage continu vérifié, sauvegarde, nouveau cluster restauré, application basculée, `verify --expect-head` contre la tête relevée avant. Puis désinstallation : plus aucune ressource de la release, après le nettoyage documenté de la tâche en échec du scénario 7 et du Secret du certificat de l'entrée (écrit par cert-manager).

Job `cluster` de la CI : après le job `image`, dont il reprend les images amd64 de l'application, du proxy et d'oauth2-proxy ; diagnostic (pods, événements, journaux) en cas d'échec ; cluster détruit quoi qu'il arrive. La publication attend qu'il passe.

### Authentification et entrée réseau (PR D1)

L'interface n'était jointe par aucun réseau (ADR 004). #### oauth2-proxy : image construite depuis le binaire publié (option B)

Relevé du 30/09/2026, version 7.15.4 : les binaires de l'image officielle (`quay.io/oauth2-proxy/oauth2-proxy:v7.15.4`, manifestes `sha256:97038fe4…` pour amd64 et `sha256:0de5b0e5…` pour arm64) **ne correspondent pas aux empreintes SHA-256 publiées dans la release GitHub** (fichiers `*-sha256sum.txt`). Méthode : binaire extrait de chaque image (`docker create` puis `docker cp` de `/bin/oauth2-proxy`), empreinte calculée (`shasum -a 256`), comparée à celle de la release : amd64 `3c48a5a1…` contre `d2cc1a81…` publiée, arm64 `a2da41ed…` contre `dd70759f…`. Rien ne relie donc le binaire de l'image officielle à la release vérifiable. Décision du propriétaire : option B.

- **Construction** (`docker/oauth2-proxy/Dockerfile`) : archive de la release téléchargée et vérifiée par son empreinte (`ADD --checksum`), binaire extrait comparé à l'empreinte publiée pour son architecture (`sha256sum --check --strict`, échec sinon) ; licence d'oauth2-proxy figée au commit de l'étiquette ; licence de chaque module Go lié au binaire (`go version -m`), téléchargées à leur version exacte et vérifiées par la base de sommes de Go, un module sans licence arrêtant la construction ; base distroless `static-debian13` non root, par empreinte ; seuls le binaire et les licences dans l'image finale. Vérifiée (`pytest -m oauth2proxy --oauth2-proxy ÉTIQUETTE` : non root, sans shell, version, binaire identique à l'empreinte publiée, licences), inventoriée, scannée, publiée et signée comme les autres images (jobs `image` et `publication`).
- **Exceptions de scan** (`securite/exceptions-vulnerabilites.yaml`, décidées le 30/09, expirent le 30/10/2026) : deux avis hauts de `google.golang.org/grpc` v1.83.0 (GHSA-2v4p-qf9q-27wj, GHSA-vp52-pcj8-j9qc) et deux de `golang.org/x/crypto` v0.55.0 (GO-2026-6354, GO-2026-6355), liés au binaire publié. `govulncheck -mode=binary` n'en atteint aucun depuis le code d'oauth2-proxy, qui ne sert pas de gRPC. Reconstruire avec des modules plus récents rendrait le binaire différent de celui dont la release publie l'empreinte : on attend la version suivante.

#### Vérification du jeton, zéro confiance

oauth2-proxy transmet le jeton d'identité signé (`Authorization: Bearer`, `--pass-authorization-header`) et retire les en-têtes d'identité reçus du client (`--skip-auth-strip-headers`, vrai par défaut). L'interface (`web --identite en-tetes`) vérifie ce jeton à chaque requête (`adapters/oidc.py`, règles pures dans `domain/identity.py`) ; sans jeton valide : 401, tracé.

- **Algorithmes** : liste fermée, celle que publie le fournisseur (`id_token_signing_alg_values_supported`), restreinte aux algorithmes asymétriques ; jamais `none`, jamais HMAC. L'algorithme de l'en-tête est contrôlé avant toute recherche de clé.
- **Revendications exigées** : `exp`, `iat`, `iss`, `aud`, `sub` ; émetteur et audience comparés exactement (l'audience est l'identifiant du client). **Tolérance d'horloge : 30 s**, sur `exp`, `iat` et `nbf`.
- **Émetteur** : HTTPS exigé (HTTP admis sur la boucle locale, pour les tests) ; le document de découverte doit annoncer le même émetteur ; `jwks_uri` et `end_session_endpoint` en HTTPS ; aucune redirection suivie ; autorité de certification réglable (`--oidc-ca`).
- **Clés publiques** : récupérées par le proxy de sortie (`HTTPS_PROXY`, lu par la bibliothèque standard), gardées 5 minutes, relues sur un `kid` inconnu au plus une fois par 30 s (`PyJWKClient`) : une rotation chez le fournisseur est prise en compte en 30 s au plus, et un `kid` forgé ne déclenche pas une rafale de requêtes. Fournisseur injoignable : 503 explicite, tracé ; jamais d'accès accordé par défaut.
- **Démarrage refusé** si l'interface n'écoute pas seulement sur 127.0.0.1 (`--host`, `--ecoute-non-locale`), sans émetteur, sans audience ou sans adresse publique HTTPS.
- **Tests d'attaque** (`tests/test_identite.py`, fournisseur factice local) : `none`, confusion RS256/HS256 avec la clé publique pour secret, autre émetteur, autre audience, jeton expiré, écart d'horloge au-delà de la tolérance, clé inconnue, `kid` forgé, revendication absente, jeton illisible, émetteur en HTTP, découverte qui annonce un autre émetteur ; rotation des clés, relecture bornée.

#### Sessions et déconnexion

- **Durées** (validées le 30/09) : session d'oauth2-proxy de 8 h (`cookie-expire`), revalidée auprès du fournisseur toutes les 5 minutes (`cookie-refresh`, jeton de rafraîchissement : un compte retiré perd l'accès dans ce délai). Dex, dans les tests : jeton d'identité de 10 minutes, jeton de rafraîchissement abandonné après 1 h d'inactivité, 8 h au plus. Cluster de test : session de 2 minutes, revalidée chaque minute, pour que le scénario d'expiration l'attende.
- **Écran d'accord non forcé** (décision du 30/09) : oauth2-proxy 7.15.4 envoie `approval_prompt=force` quand ni `--prompt` ni `--approval-prompt` n'est réglé (`pkg/apis/options/legacy_options.go`), et certains fournisseurs (Dex, Google) demandent alors l'accord à chaque connexion. Le chart fixe `--approval-prompt=auto` (`authentification.accord`, `auto` ou `force`) : pas d'écran forcé, et les fournisseurs qui ne connaissent pas ce paramètre, antérieur à OIDC, l'ignorent. Le paramètre OIDC `prompt` n'est pas utilisé : aucune de ses valeurs ne laisse le comportement par défaut du fournisseur (`none` interdit tout écran, `login`, `consent` et `select_account` ajoutent une étape). Testé au rendu, et dans le cluster : la connexion par le navigateur ne passe par aucun écran d'accord.
- **Cookie de session** : `Secure`, `HttpOnly`, `SameSite=Lax`, chiffré (clé en fichier) ; portées demandées `openid profile groups offline_access`, jamais `email` (minimisation).
- **Déconnexion** : formulaire de l'interface (`POST /deconnexion`, CSRF), page de transition (la politique `form-action 'self'` bloquerait une redirection vers le fournisseur), fin de session d'oauth2-proxy (`/oauth2/sign_out`, cookie retiré), puis, si le chart le demande (`authentification.deconnexionFournisseur`) et que le fournisseur publie `end_session_endpoint`, fin de session chez lui ; le client y est désigné par son identifiant, jamais par son jeton. Dex 2.45.1 ne publie pas de fin de session : limite du fournisseur de test, donc du test ; réglage à activer en production.
- **Limite connue** : la session d'oauth2-proxy est tout entière dans le cookie. Après la déconnexion, le navigateur n'a plus de cookie ; un cookie volé avant, lui, reste valable jusqu'à sa prochaine revalidation (5 minutes au plus) si le fournisseur a fermé la session, jusqu'à son expiration sinon. Un stockage des sessions côté serveur (Redis) le supprimerait : hors du périmètre de la D1, noté pour la production.

#### oauth2-proxy en conteneur annexe natif

Décision du propriétaire (30/09) : l'ordre d'arrêt ne doit pas dépendre d'un délai choisi à la main. oauth2-proxy était un second conteneur ordinaire du pod, maintenu ouvert pendant l'arrêt de l'interface par une pause preStop de 70 s (pause avant l'arrêt plus délai laissé aux requêtes). Il devient un conteneur annexe natif : conteneur d'initialisation redémarré (`restartPolicy: Always`, stable depuis Kubernetes 1.33), le dernier des conteneurs d'initialisation (après la copie du modèle, quand elle a lieu).

- **Démarrage** : le kubelet ne démarre l'interface qu'une fois la sonde de démarrage d'oauth2-proxy passée (`/ping`) ; il le relance s'il s'arrête, comme un conteneur ordinaire.
- **Arrêt** : le kubelet arrête d'abord l'interface (pause preStop, puis SIGTERM et fin des requêtes), puis, une fois qu'elle est sortie, les conteneurs annexes. oauth2-proxy n'a plus de pause preStop ; au SIGTERM, il ferme ses ports d'écoute et laisse finir les requêtes en cours (`http.Server.Shutdown`, lu dans `pkg/proxyhttp/server.go` de la v7.15.4).
- **Ports nommés** : Kubernetes 1.36 résout un port nommé porté par un conteneur annexe natif pour un Service (`FindPort`, `staging/src/k8s.io/endpointslice/utils.go`) ; kube-router, qui applique les règles réseau dans k3s, ne lit les ports nommés que dans les conteneurs ordinaires (`pkg/controllers/netpol/policy.go`). La règle réseau d'entrée désigne donc oauth2-proxy par son numéro de port.
- **Quota** : ses ressources comptent avec celles du pod, qu'il accompagne toute sa vie ; le test du quota les additionne.
- **Tests** : au rendu (`restartPolicy: Always`, sonde de démarrage, aucune pause preStop, dernier des conteneurs d'initialisation, règle réseau par numéro de port) ; dans le cluster, oauth2-proxy démarré avant l'interface dans chaque pod ; un pod arrêté, l'état de ses conteneurs, relevé en continu, ne montre jamais oauth2-proxy arrêté tant que l'interface tourne, et oauth2-proxy s'arrête dès qu'elle est sortie. Les événements « Stopping container » ne le disent pas : le kubelet 1.36 les émet pour chaque conteneur dès le début de l'arrêt, puis fait attendre les conteneurs annexes (`killContainer`, `ordering.waitForTurn`, `pkg/kubelet/kuberuntime/kuberuntime_container.go`) ; une première version du scénario s'y fiait et échouait.
- **Piste écartée, requête perdue du troisième passage** : la sonde du scénario de mise à jour ne passe pas par oauth2-proxy (service `-sante`, port de santé de l'interface), et oauth2-proxy restait ouvert plus longtemps que l'interface. Le changement ne se justifie pas par elle, mais par l'ordre garanti.

#### Formulaires entre réplicas : clés CSRF partagées

Défaut trouvé par le cluster (30/09) : chaque processus tirait son propre secret CSRF (`adapters/web/security.py`) ; derrière Traefik, un formulaire servi par un réplica et envoyé à l'autre était refusé (403), une fois sur deux, et un redémarrage invalidait les formulaires ouverts. Les scénarios de la C3 passaient par une redirection de port vers un seul pod. Décision du propriétaire (30/09) : un secret partagé, monté en fichier, avec rotation sans coupure.

- **Clés** : Secret `cdg-csrf` (`authentification.secretCsrf`), tout entier monté dans le seul conteneur de l'interface, sans `subPath` : `courante` signe et vérifie, `precedente` ne fait que vérifier, le temps d'une rotation ; 32 caractères au moins. `web --cles-csrf DOSSIER`, exigé avec `--identite en-tetes` : lues au lancement (une clé absente ou trop courte l'arrête, sans jamais la montrer), puis relues à chaque formulaire, ce qui applique une rotation sans redémarrage. Sans l'option (interface locale, un seul processus), une clé tirée par le processus, comme avant.
- **Durée de vie d'un formulaire** : le jeton porte son heure d'émission, sous la signature (HMAC-SHA256 du cookie et de l'heure) ; il vaut 8 heures, la durée de session par défaut, avec une minute d'écart d'horloge admis entre réplicas. Sans elle, on ne saurait pas quand retirer une ancienne clé.
- **Rotation en trois temps** (`docs/exploitation.md`), écart assumé avec la procédure en deux temps demandée (ajouter, attendre, retirer) : le kubelet met à jour le fichier de chaque pod à son rythme, et un réplica en avance signerait avec une clé que l'autre ne connaît pas encore. La nouvelle clé est donc d'abord annoncée, en `precedente` (vérification seulement), puis elle signe, l'ancienne passant en `precedente` le temps qu'expirent les formulaires ouverts, puis l'ancienne est retirée. Mêmes deux emplacements, sans troisième clé.
- **Tests** (`tests/test_csrf.py`) : formulaire d'un réplica accepté par l'autre avec les mêmes clés, refusé sans ; ancienne clé acceptée pendant la transition, refusée après son retrait ; deux réplicas mis à jour à des instants différents acceptent les formulaires l'un de l'autre, et le refus qui se produirait sans l'annonce ; expiration, jeton venu du futur ou mal formé ; aucune clé dans les journaux, les messages d'erreur ni les représentations. Scénario du cluster : formulaire obtenu d'un réplica, accepté par l'autre, refusé altéré.

#### Journal des accès

Distinct du journal des décisions : JSON sur la sortie standard (`journal: cdg.acces`), champs en liste blanche à leur source (`adapters/web/acces.py`) : `motif`, `iss`, `sub`, `methode`, `chemin`, `statut`, `session_fournisseur`. Jamais de courriel, de nom, de jeton ni de cookie.

- **Événements de l'interface** : `acces_refuse` (401, avec le motif : `jeton_absent`, `signature_invalide`, `cle_inconnue`, `jeton_expire`…), `fournisseur_injoignable` (503), `deconnexion` (`iss`, `sub`, état de la session du fournisseur). Refus 403 et quatre yeux : PR D2.
- **Connexions** : journal d'authentification d'oauth2-proxy, réduit au `sub` : format de ligne imposé (`journal`, `evenement`, `statut`, `sub`), revendication de courriel remplacée par `sub` (`--oidc-email-claim=sub`, oauth2-proxy journalisant le courriel de la session), journal des requêtes coupé.
- **Traefik** : journal d'accès en JSON, en-têtes écartés (défaut du chart) : ni cookie ni jeton.

#### Entrée (Traefik)

Ressources du chart de l'application, créées seulement avec l'authentification (le chart refuse une entrée sans elle) :

- **TLS 1.2 au moins** (`TLSOption`, `sniStrict`) ; certificat délivré par cert-manager (`ingress.emetteurCertificat` : autorité de test dans le cluster, ACME ou autorité de l'entreprise en production).
- **HSTS** (un an, sans `includeSubDomains` ni `preload` : le domaine de production n'est pas connu) ; **HTTP redirigé vers HTTPS** (redirection permanente, routeur à part).
- **Taille maximale d'un envoi** : celle de l'interface, calculée par la même formule depuis `config/decision.yaml` (`input.max_chars` × 4 + 64 Kio) ; refusée par Traefik (413) avant oauth2-proxy.
- **Débit** : 20 requêtes par seconde en moyenne, rafales de 40, par adresse de la connexion (`ipStrategy.depth: 0`), jamais par un en-tête du client. L'adresse vue par Traefik est vérifiée dans le cluster (scénario ci-dessous : l'adresse de chaque pod client dans son journal d'accès) ; le service de Traefik est en `externalTrafficPolicy: Local`, qui préserve l'adresse du client derrière un équilibreur de charge. En production derrière un équilibreur qui traduit les adresses, activer le protocole PROXY ou des adresses de confiance : choix d'exploitation, documenté.
- **Règle réseau** : le port d'oauth2-proxy n'admet que les pods de Traefik ; l'interface n'écoute que sur la boucle locale du pod.

Formulaire de revue montré au seul relecteur.

Règle pure : refusée à qui a lancé l'analyse (même émetteur et même `sub`) et à tout autre canal que celui de l'analyse (analyse dans l'interface, puis décision par la même personne via la CLI sous un opérateur choisi librement) ; admise en accès d'urgence, tracé et scellé ; hors de propos pour l'expiration (NO_GO système). Une analyse antérieure aux rôles, sans acteur connu, ne se tranche qu'en accès d'urgence, ou s'expire.

Non exigé par défaut, et avec Dex, qui n'en fournit pas : avertissement au démarrage de l'interface et dans les notes d'installation du chart. **Prérequis de production.**

Les enregistrements v1 (sans version, relecteur nommé) restent vérifiables (la vérification recalcule tout sur le JSON stocké, jamais d'un modèle relu) et rejouables par leurs modèles, figés (`DecisionRecordV1`) ; une version inconnue est refusée. Aucun ne se rejoue avec le code courant. Cause, établie le 30/09 : l'empreinte de configuration porte sur la configuration validée par le modèle de l'époque (`model_dump`, valeurs par défaut comprises), pas sur le fichier ; rechargé par le modèle courant, le même fichier gagne les champs ajoutés depuis, et son empreinte change. Recalculée avec le code du commit `84051d2` (26/09), celui de ces scellements, l'empreinte correspond (`d8c8bf00…`), et les 5 enregistrements s'y rejouent à l'identique. Faute de configuration archivée, ils restent non rejouables par le code courant ; l'archivage de chaque configuration au scellement fait l'objet de la PR suivante. Ils ne portent pas non plus la version de leur code : c'est l'historique du dépôt qui a désigné `84051d2`.
- **Version du code scellée** (décision du propriétaire du 30/09, ajoutée à la D2 avant la fusion, le format v2 n'étant pas encore en production) : chaque enregistrement v2 porte `code_version`, celle de l'analyse, posée par `run_contract` avec la configuration, et `sealing_code_version`, celle du processus qui scelle : le commit, et, dans le cluster, l'empreinte de l'image (`domain/version.py`). Toutes deux sont fournies, jamais devinées. Le commit est passé à la construction de l'image (`--build-arg CDG_COMMIT`), calculé par `scripts/chaine.py revision`, en CI comme dans `check.sh` : c'est celui de HEAD si le contexte de construction est exactement celui du commit (ni modification, ni ajout, ni fichier ignoré par git mais copié dans l'image), sinon « inconnu », avec la raison sur la sortie d'erreur. L'empreinte est passée au lancement par le chart (`CDG_EMPREINTE_IMAGE`) : la même que celle qui tire l'image, soit, pour l'image publiée, celle de l'index multi-architecture, que la signature et la provenance couvrent. La CLI les lit au démarrage, sans git ni registre. Sans commit (poste de développement, `uv run`), l'enregistrement porte « inconnu » ; une valeur mal formée arrête le programme ; dans le cluster, l'empreinte est exigée. Ces versions restent hors de la partie décision : `decision_hash` ne dépend que des entrées de la décision et de la configuration (critère 6), et la chaîne couvre tout. Si l'analyse et le scellement tournent sous deux versions (mise à jour entre l'analyse et la revue, ou reprise d'une analyse interrompue par un pod plus récent), les deux sont scellées, avec le constat « code modifié entre l'analyse et le scellement ». La revue n'est pas refusée pour autant, à la différence d'un changement de configuration : chaque mise à jour bloquerait sinon toutes les revues en attente. Une analyse lancée avant ce scellement porte un `code_version` nul.
- **Deux sens du rejeu** :
  - **rejeu fidèle** : même code et même configuration que la décision scellée, c'est-à-dire un commit scellé connu et égal à celui du processus qui rejoue (l'image aussi, quand elle est scellée), et la configuration de l'empreinte scellée. La décision recalculée doit être identique ; toute différence est une anomalie (journal altéré, ou calcul non déterministe), signalée comme une erreur ;
  - **réévaluation avec le code courant** : le code a changé depuis le scellement, ou sa version est inconnue, ou deux versions ont servi à l'analyse et au scellement. Une décision différente est possible et légitime (règle corrigée ou ajoutée) : elle est signalée, sans être une erreur ;
  - aujourd'hui, `replay` recalcule avec le code courant, sous la configuration courante, qui doit avoir l'empreinte scellée : c'est une réévaluation, qui ne se distingue pas encore du rejeu fidèle. La PR d'archivage des configurations rendra la configuration scellée (contrôlée par son empreinte, puis rejouée sans que celle-ci soit recalculée après validation), et comparera la version du code scellée à celle du processus pour dire lequel des deux sens s'applique.
- **Jamais de nom scellé, par l'exemple** : l'enregistrement n° 3 de ce journal porte, au format v1, un prénom en relecteur, celui du propriétaire ; il reste tel quel (on ne réécrit pas un journal chaîné), dans un journal local jamais publié, et aucun jeu de test n'en est tiré. En v2, un nom ne peut plus être scellé : l'acteur n'a pas de champ pour cela, le formulaire ne demande plus de nom, et un champ `relecteur` envoyé malgré tout est ignoré (testé).
- **Journal des accès complété** : `acces_interdit` (motif `role_manquant`, rôle requis), `quatre_yeux_refuse` (contrat), `second_facteur_manquant`, `acces_urgence` (opérateur, commande, motif) ; liste blanche élargie à `role`, `thread_id`, `operateur`, `commande`.
- **Accès d'urgence** (procédure : `docs/exploitation.md`) : quand le fournisseur est injoignable, ou pour une analyse antérieure aux rôles ; par la CLI dans le pod (`kubectl exec`), `--operateur` et `--urgence MOTIF` ; une astreinte désignée, sous un identifiant non nominatif dont la correspondance est tenue hors du projet. La sortie d'un processus lancé par `kubectl exec` part vers le terminal, pas dans les journaux du pod : l'événement est aussi écrit sur la sortie du processus principal du conteneur (`/proc/1/fd/1`), que Kubernetes collecte ; s'il ne peut l'être, l'accès est refusé. La décision est scellée avec le canal `cli` et l'accès d'urgence.

#### Hors du projet pour une vraie production

Le projet ne livre pas, et une vraie production exigerait : un gestionnaire de secrets externe (coffre, rotation centralisée ; les Secrets Kubernetes chiffrés au repos ne suffisent pas à une politique de secrets) ; un pare-feu applicatif (WAF) devant l'entrée ; une surveillance de sécurité et des alertes (collecte et corrélation des journaux d'accès, alertes sur les refus répétés et les accès d'urgence) ; un test d'intrusion ; une haute disponibilité multizone (base, entrée, fournisseur d'identité). S'y ajoute le stockage des sessions d'oauth2-proxy côté serveur (limite notée en D1).
